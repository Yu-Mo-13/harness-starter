# Harness MVP 要件定義

## 1. 文書の目的

本書は、AIコーディングエージェント向けのスキル、ルール、サブエージェントをプロジェクトへ初期導入するCLI「Harness」のMVP要件を定義する。

未確定事項は [open-issues.md](./open-issues.md) に分離し、本書には現時点で合意済みの要件のみを記載する。

## 2. プロダクト概要

Harnessは、新規プロジェクトの作成時、または既存プロジェクトへ初めてAIエージェント用の構成を導入するときに利用するCLIである。

プロジェクトを解析して技術スタックを検出し、次の資産を対象AIエージェントの所定のディレクトリへ配置する。

- スキル
  - `.agents/skills/*`
  - `.claude/skills/*`
- ルール
  - `.agents/rules/*`
  - `.claude/rules/*`
- サブエージェント
  - `.agents/agents/*`
  - `.claude/agents/*`

## 3. 解決する課題

- AIエージェントごとに異なるディレクトリ構成やファイル形式を手作業で整備する必要がある
- プロジェクトの技術スタックに適したスキルを判断し、配置する負担がある
- コーディング規則やアーキテクチャ方針をAIエージェントへ一貫して伝えにくい
- レビュー、テスト、設計などの役割を持つサブエージェントを導入する手順が統一されていない
- モノレポにおいて、アプリケーションごとに異なる構成を安全に導入しづらい
- 既存ファイルとの競合や意図しない上書きを避けながら導入内容を確認する手段が必要である

## 4. 想定ユーザー

- AIコーディングエージェントを利用する開発者
- プロジェクト開始時のAI開発環境を標準化したいチーム
- モノレポ内の複数アプリケーションへ、それぞれ適切な設定を導入したい開発者

## 5. 対象ユースケース

### 5.1 新規プロジェクトへの導入

プロジェクト作成後に`harness init`を実行し、技術スタックに合ったスキルと、ユーザーが選択したルールおよびサブエージェントを配置する。

### 5.2 既存プロジェクトへの初回導入

既存のマニフェスト、ロックファイル、ディレクトリ構成などを解析し、既存ファイルを保護しながらAIエージェント用の構成を配置する。

### 5.3 モノレポへの導入

リポジトリ内のアプリケーションまたはサービスを検出し、ユーザーが選択したアプリケーション単位で個別の構成を決定して配置する。

## 6. 基本方針

### 6.1 テンプレートの供給元

- 配置する資産はHarnessに同梱された公式テンプレートのみを使用する
- 外部Gitリポジトリ、URL、マーケットプレイスからテンプレートを取得しない
- ユーザー独自テンプレートの登録はMVP対象外とする

### 6.2 資産ごとの決定方法

| 資産 | 決定方法 | 初期状態 |
| --- | --- | --- |
| スキル | 検出された技術スタックから自動決定 | 自動選択 |
| ルール | カテゴリー別にユーザーが選択 | すべて未選択 |
| サブエージェント | 役割別にユーザーが選択 | すべて未選択 |

### 6.3 推薦表示

- ルールとサブエージェントには、検出結果に基づく「おすすめ」を表示できる
- おすすめには推薦理由を表示する
- おすすめであっても自動選択しない
- ユーザーが明示的に選択したものだけを導入する
- ルールまたはサブエージェントを一つも選択せずに進めることを許可する

## 7. 対象AIエージェント

MVPでは次の出力先を対象とする。

- `.agents`形式
- `.claude`形式

ユーザーはアプリケーションごとに一方または両方を選択できる。

## 8. 対象技術スタック

### 8.1 フロントエンドおよびJavaScript/TypeScript

- JavaScript
- TypeScript
- React
- Next.js
- Node.js
- Vitest
- Playwright

### 8.2 バックエンド

| 言語 | MVP対象フレームワーク |
| --- | --- |
| PHP | Laravel、Symfony |
| Ruby | Ruby on Rails |
| Java | Spring Boot |
| Python | Django、FastAPI |

フレームワークを検出できない場合でも、対応言語が検出できれば言語単体のスキルを導入できる。

### 8.3 スキルの構成

言語共通スキルとフレームワーク固有スキルを分離し、検出されたスタックに対応するスキルを合成する。重複するスキルIDは一度だけ導入する。

例として、Laravelプロジェクトでは次のスキルを自動選択する。

```text
php-development
laravel-development
```

## 9. プロジェクト解析

### 9.1 検出対象

Harnessは、次の情報を読み取り専用で検出する。

- プログラミング言語とバージョン
- フレームワークとバージョン
- パッケージマネージャー
- テストフレームワーク
- LinterおよびFormatter
- ビルドツール
- CI構成
- モノレポまたはワークスペース構成
- アプリケーション、サービス、ライブラリの候補
- 既存の`.agents`および`.claude`構成

### 9.2 主な検出元

- `package.json`、JavaScript/TypeScript系ロックファイル、ワークスペース定義
- `composer.json`、`composer.lock`
- `Gemfile`、`Gemfile.lock`、`.ruby-version`
- `pom.xml`、`build.gradle`、`build.gradle.kts`、Gradle settings
- `pyproject.toml`、`requirements*.txt`、Python系ロックファイル
- フレームワーク固有のエントリーポイントや設定ファイル
- CI設定および主要ディレクトリ構成

依存関係を確定できるロックファイルがある場合は、宣言のみのマニフェストより優先する。

### 9.3 検出結果の確認

- 検出結果と検出根拠をユーザーへ表示する
- ユーザーは誤検出されたスタックを解除できる
- ユーザーは検出できなかったスタックを追加できる
- スタックの修正に応じて自動選択されるスキルを再計算する
- 既存プロジェクトの実際のバージョンを尊重し、最新版の仕様を無条件に適用しない

## 10. アプリケーション単位の導入

### 10.1 アプリケーション候補

Harnessは検出した候補を次の種別として表示する。

- `application`: 実行またはデプロイ可能なアプリケーション
- `service`: APIやワーカーなどの独立サービス
- `library`: 共有ライブラリまたはパッケージ
- `unknown`: 種別を確定できないプロジェクト

ユーザーは導入対象の候補を明示的に選択する。初期状態ではすべて未選択とする。

### 10.2 個別設定

選択したアプリケーションごとに、次の項目を独立して決定する。

1. 対象AIエージェント
2. 技術スタック
3. 自動導入するスキル
4. ユーザーが選択するルール
5. ユーザーが選択するサブエージェント

あるアプリケーションの選択内容を別のアプリケーションへ暗黙に適用しない。

### 10.3 配置先

単一アプリケーションのリポジトリではリポジトリルートへ配置する。モノレポでは、原則として選択した各アプリケーションのルート配下へ配置する。

```text
apps/
├── web/
│   ├── .agents/
│   └── .claude/
└── api/
    ├── .agents/
    └── .claude/
```

## 11. ルール

### 11.1 カテゴリー

ルールは少なくとも次のカテゴリーに分類する。

- コーディング規則
- アーキテクチャパターン
- デザインパターン
- 開発プロセス

### 11.2 選択操作

- カテゴリーごとに選択肢を表示する
- 各ルールの概要を確認できる
- 技術スタックに適したルールを上位表示できる
- おすすめラベルと推薦理由を表示する
- 初期状態では選択しない
- 選択画面へ戻った場合も選択状態を保持する

## 12. サブエージェント

### 12.1 選択方式

サブエージェントは技術スタックから自動決定せず、役割ベースでユーザーが選択する。

### 12.2 MVP候補

- Reviewer
- Tester
- Architect
- Debugger

追加候補としてSecurity ReviewerおよびDocumenterを想定するが、最終的なMVP収録範囲は残課題とする。

### 12.3 選択操作

- 役割、利用場面、期待する成果を表示する
- プロジェクト特性に応じたおすすめと推薦理由を表示できる
- 初期状態では選択しない
- 選択画面へ戻った場合も選択状態を保持する
- 選択したルールと関連するサブエージェントを案内できる
- 関連項目をユーザー確認なしに自動追加しない

## 13. 対話型導入フロー

`harness init`は次の順序で進行する。

1. リポジトリを解析する
2. アプリケーション候補を表示し、導入対象を選択する
3. アプリケーションごとに対象AIエージェントを選択する
4. アプリケーションごとに技術スタックを確認・修正する
5. 技術スタックからスキルを自動決定する
6. アプリケーションごとにルールを選択する
7. アプリケーションごとにサブエージェントを選択する
8. 全アプリケーションの導入イメージを表示する
9. 内容を選び直すか、導入を確定する
10. 確定後にファイルを生成する

## 14. 導入イメージと選び直し

MVPでは独立した`dry-run`機能を設けず、書き込み前に必ず導入イメージを表示する。

導入イメージには次を含める。

- 導入対象アプリケーション
- 対象AIエージェント
- 検出または修正された技術スタック
- 自動導入されるスキル
- ユーザーが選択したルール
- ユーザーが選択したサブエージェント
- 作成予定ファイル
- 既存ファイルとの競合

ユーザーは導入イメージから次の操作を実行できる。

- 特定アプリケーションの設定へ戻る
- 導入対象アプリケーションを選び直す
- 技術スタックを修正する
- ルールを選び直す
- サブエージェントを選び直す
- 導入を確定する
- キャンセルする

前の画面へ戻った場合も、それまでの選択状態を保持する。

## 15. 書き込みの安全性

- 最終確定まではファイルを変更しない
- キャンセル時はファイルを一切変更しない
- 管理対象外のファイルを削除しない
- 既存ファイルを暗黙に上書きしない
- すべての競合を確定前に表示する
- 複数アプリケーションへの導入は一つの処理単位として扱う
- 書き込み途中で失敗した場合に、中途半端な導入状態を残さない
- アプリケーションコード自体は変更しない

## 16. 生成後の扱い

- 生成されたスキル、ルール、サブエージェントはユーザーが所有する
- ユーザーは生成後のファイルを自由に編集できる
- 生成後にHarnessを常時利用しなくても対象AIエージェントを使用できる
- 生成物はプロジェクトとともにGit管理できる

再実行、生成物の識別、更新方法の詳細は残課題とする。

## 17. MVPの主要コマンド

```text
harness init
harness validate
```

- `harness init`: プロジェクト解析、選択、プレビュー、初期配置を行う
- `harness validate`: 配置済みの構成が対象形式として妥当か検証する

追加コマンドおよび非対話オプションは残課題とする。

## 18. MVP対象外

- 外部テンプレートの取得
- テンプレートマーケットプレイス
- ユーザー独自テンプレートの登録
- GUI
- クラウド同期
- リモートでのAIエージェント実行
- ルート設定から子アプリケーションへの暗黙の継承
- 生成済みファイルの無断更新または削除
- あらゆる言語、フレームワーク、AIエージェントへの対応

## 19. 受け入れ基準

- 新規プロジェクトと既存プロジェクトで`harness init`を開始できる
- 単一アプリケーションとモノレポを識別できる
- モノレポ内の複数アプリケーション候補を表示できる
- ユーザーがアプリケーション単位で導入対象を選択できる
- 対象言語およびフレームワークをマニフェストやロックファイルから検出できる
- 検出結果の根拠を表示し、ユーザーが修正できる
- 技術スタックから導入スキルが一意に決まる
- フレームワークなしでも言語スキルを導入できる
- ルールをカテゴリー別に選択できる
- サブエージェントを役割別に選択できる
- おすすめ項目が自動選択されない
- ルールとサブエージェントを選択せずに進められる
- 確定前に全アプリケーションの導入イメージを確認できる
- 導入イメージから各選択画面へ戻れる
- 選択画面へ戻っても選択状態が保持される
- プレビュー完了まではファイルが変更されない
- キャンセル時にファイルが変更されない
- 既存ファイルが暗黙に上書きされない
- 確定後に対象ファイルを一括生成できる
- 書き込み失敗時に一部だけ導入された状態を残さない
- 生成後にHarnessなしで対象AIエージェントを利用できる
