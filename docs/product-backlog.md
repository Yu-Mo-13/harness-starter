## 1. 目的

本書は、[機能一覧](./feature-list.md)をユーザー価値単位のストーリー候補へまとめた初期バックログである。GitHub Issueを正本とするまでの投入元として使用し、優先順位はプロダクトマネージャーがGitHub Projects上で更新する。

運用中の正本は[Harness MVP Project](https://github.com/users/Yu-Mo-13/projects/7)とする。Issueタイトルの`EN-*`、`US-*`、`P-*`、`F-*`で本書および要件文書へ追跡する。

見積もりは初期仮説であり、Definition of Readyを満たす際にエンジニアとQAが再見積もりする。8ポイントの項目はリファインメントで分割を検討する。

## 3. ストーリー別受入条件

### EN-001 TypeScript CLI開発基盤

- Given clean checkoutとサポート対象Node.js、when 依存関係をlockfileから導入する、then `harness init`と`harness validate`のエントリーポイントを起動できる
- Given 開発環境、when committed scriptを実行する、then `build`、`test`、`lint`、`format`を再現可能に検証できる
- Given pull request、when CIを実行する、then macOS、Linux、Windowsの必須チェック結果を確認できる
- Given npm packageをpackする、when 内容を検査する、then CLI実行物と将来の同梱テンプレートに必要な構造だけが含まれる
- QAはclean install、未対応Node.js、bin起動、package内容、各OSの最低限のsmoke testを検証する

### US-001 リポジトリ解析と根拠表示

- Given 対応する構成ファイルを含むリポジトリ、when 解析する、then 言語、バージョン、開発ツール、既存AI構成と各根拠が表示される
- Given マニフェストとロックファイルの内容が異なる、when 依存関係を判定する、then ロックファイルが優先され、その根拠が示される
- Given 同一のfixture、when 複数回またはオフラインで解析する、then 外部通信なしで同一結果になる
- Given `.env`や資格情報ファイル、when 解析する、then 内容を読み取り・表示・送信しない
- QAは対応スタックごとのfixture、矛盾するシグナル、壊れた構成ファイル、空のリポジトリを検証する

### US-002 モノレポ候補の検出と対象選択

- Given 単一アプリケーション、when 解析する、then リポジトリルートが候補になる
- Given 複数workspace、when 解析する、then 各候補のルート、根拠、`application`、`service`、`library`、`unknown`の種別が表示される
- Given 候補一覧、when 初めて表示する、then 全候補が未選択である
- Given 利用者が一部だけ選択する、when 次へ進む、then 選択した候補だけが設定対象になる
- QAは入れ子workspace、重複候補、symlink、空workspace、異なるパス区切りを検証する

### US-003 候補別の対象AIエージェント選択

- Given 選択済み候補、when 対象を設定する、then Codex、Claude Code、または両方を候補ごとに選べる
- Given 複数候補に異なる設定、when 前後に移動する、then 設定が混ざらず保持される
- Given 単一構成とモノレポ、when 配置先を計算する、then 要件に定めた各ルートになる
- QAは候補追加・解除後の状態、戻る操作、同名候補を検証する

### US-004 技術スタック確認とスキル自動選定

- Given 検出済みスタック、when 表示する、then 候補ごとに名前、バージョン、根拠が確認できる
- Given 誤検出の解除または未検出スタックの追加、when 確定する、then スキルが再計算される
- Given 言語とフレームワーク、when 選定する、then 共通・固有スキルが合成され、重複IDが除外される
- Given 対応言語だけを検出、when 選定する、then 言語単体スキルが選ばれる
- QAは全対象スタック、複数バージョン、EOL警告、競合バージョンをデータ駆動で検証する

### US-005 ルール選択

- Given ルール一覧、when 表示する、then 4カテゴリー、概要、おすすめ理由が確認でき、全項目が未選択である
- Given おすすめ項目、when 画面を開く、then 自動選択されない
- Given 0件または任意のルールを選択、when 前後に移動する、then その状態で進行でき、選択が保持される
- Given 競合または依存するルール、when 選択する、then 決定済みの`P-006`に従った説明と制御が行われる
- QAはキーボード操作、長い説明、0件、競合、戻る操作を検証する

### US-006 サブエージェント選択

- Given サブエージェント一覧、when 表示する、then 役割、利用場面、期待成果、おすすめ理由が確認でき、全項目が未選択である
- Given 関連ルール、when 一覧を表示する、then 関連候補を案内するが自動追加しない
- Given 0件または任意の候補を選択、when 前後に移動する、then その状態で進行でき、選択が保持される
- Given 対象AIエージェント、when 権限へ変換する、then 最小権限となり、変換不能な権限を黙って破棄しない
- QAは各対象、0件、複数選択、戻る操作、危険な権限の拒否を検証する

### US-007 導入プレビューと確定

- Given 全候補の設定、when 最終画面へ進む、then 対象、スタック、資産、作成予定ファイル、全競合がまとめて表示される
- Given プレビュー、when 任意の選択画面へ戻る、then 既存選択を保持したまま変更できる
- Given 確定前またはキャンセル、when 終了する、then ファイルシステムに変更がない
- Given 利用者の明示的な確定、when 続行する、then 初めて書き込み処理を開始する
- QAは各戻り先、複数競合、キャンセル、終了シグナル、非TTY時の扱いを検証する

### US-008 テンプレート変換

- Given 共通テンプレート、when 対象別に変換する、then 公式の配置・形式・必須メタデータに準拠する
- Given 共通形式で安全に表現できない内容、when 変換する、then 対象別テンプレートへ差し替えるか明示的に失敗する
- Given 未定義変数、未対応項目、変換不能な設定、when 変換する、then 警告またはエラーとなり黙って欠落しない
- Given 同一入力・テンプレート・アダプターバージョン、when 生成する、then byte単位で同一になる
- QAはスキーマ、snapshot、出典・ライセンス、危険なコマンド、対象CLI構文を検証する

### US-009 安全な一括生成

- Given 複数候補、when 書き込む、then すべてを一つの処理単位として反映する
- Given 途中の任意地点で失敗、when 復旧する、then Harnessによる変更が戻され、既存内容が維持される
- Given 既存またはユーザー編集済みファイル、when 生成する、then 暗黙に上書き・削除しない
- Given 生成成功、when Harnessを終了する、then 生成物だけで対象AIエージェントが利用でき、Git管理と編集ができる
- QAは権限エラー、容量不足、競合、symlink、改行、パス区切り、プロセス中断を検証する

### US-010 配置済み構成の検証

- Given 有効な構成、when `harness validate`を非対話で実行する、then 成功を示す終了コードになる
- Given 無効または不足した構成、when 実行する、then 対象ファイル、原因、修正方法と失敗終了コードが示される
- Given 機密情報を含む環境、when 通常・詳細ログを出力する、then 機密値が含まれない
- QAは対象別の有効・無効fixture、複数エラー、各OS、非TTY、終了コードを検証する

### US-011 リリース互換性証跡

- Given リリース候補、when 互換性検証する、then CodexとClaude Codeの実CLIが生成物を認識する
- Given リリース、when 公開準備する、then 検証済みCLIバージョン、参照仕様、確認日、テンプレートとアダプターバージョンが記録される
- Given 対象CLIの仕様変更、when 検証に失敗する、then リリースを停止し、互換性問題を追跡できる
- QAは固定バージョンと更新候補の両方で互換性ジョブの証跡を確認する

### US-012 クロスプラットフォームとアクセシビリティ

- Given 同一fixture、when macOS、Linux、Windowsで処理する、then OS固有差異を除いて同じ論理結果になる
- Given 色を無効化した端末、when 操作する、then 色なしでも状態とエラーを識別できる
- Given キーボードのみの操作、when `harness init`を実行する、then 全フローを完了またはキャンセルできる
- QAはOS別CIに加え、改行、権限、symlink、狭い端末、`NO_COLOR`、非TTYを検証する

## 5. 推奨する最初の投入順

最初のStory Sprintでは、`P-009`、`P-010`、US-001、US-002をReadyにする。最初のImplementation SprintではEN-001を完了し、次のPlanningでUS-001のSub-issueから薄い縦切りを選ぶ。Sprint Reviewではclean installからのCLI起動、実際のfixture、検出根拠を確認する。

US-001、US-002、US-004、US-007〜US-009は8ポイントのため、リファインメント時に対象スタック、単一/モノレポ、正常/競合フローなどで分割する。ただし分割後も、利用者が確認できる結果と自動テストを各Issueに含める。
