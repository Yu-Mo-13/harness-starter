# Harness MVP 残課題

## 1. 文書の目的

本書は、Harness MVPの要件定義において未確定の事項、実装前に判断が必要な事項、および推奨される初期案を記録する。

確定済みの要件は [requirements.md](./requirements.md) を参照する。

## 2. 優先度の定義

| 優先度 | 意味 |
| --- | --- |
| P0 | 実装開始前に決定が必要 |
| P1 | 該当機能の実装前に決定が必要 |
| P2 | MVP期間中に決定すればよい |

## 3. P0: 実装開始前に決定する事項

### 3.1 プロジェクト解析および推薦にAIを使用するか

検討事項:

- マニフェストやディレクトリ構成に基づく決定的なルールだけで解析するか
- LLMを利用してプロジェクト種別や推薦内容を判断するか
- LLMを利用する場合のAPIキー、費用、ネットワーク、プライバシーをどう扱うか

推奨案:

- MVPはルールベースで解析および推薦する
- LLM APIを使用しない
- オフラインで同一入力から同一結果を得られるようにする

### 3.2 実装言語と配布方法

検討事項:

- TypeScriptなどのランタイム依存CLIとして配布するか
- GoまたはRustなどで単一バイナリとして配布するか
- npm、Homebrew、GitHub Releasesなど、どの導入経路を提供するか
- PHP、Ruby、Java、Pythonプロジェクトでも追加ランタイムなしで利用できる必要があるか

推奨案:

- 開発速度を優先する場合はTypeScriptとnpmで開始する
- 利用環境への依存を減らすことを優先する場合は単一バイナリを選ぶ

### 3.3 対応OS

検討事項:

- macOS、Linux、WindowsのどこまでをMVP対象にするか
- パス区切り、改行コード、ファイル権限、シンボリックリンクをどう扱うか

推奨案:

- MVPはmacOSとLinuxを対象とする
- Windowsは後続リリースで追加する

### 3.4 対応先の正式な仕様と互換性

検討事項:

- `.agents`および`.claude`の正確なディレクトリ構成と必須メタデータ
- サブディレクトリに配置した設定が各AIエージェントからどのように認識されるか
- 対応先の仕様バージョンをどこまで保証するか
- 仕様変更を検知し、追従する方法

推奨案:

- 対応先ごとにアダプターを分離する
- サポートする仕様またはCLIバージョンを明記する
- 未対応の設定値を黙って破棄せず警告する
- 各対応先の実環境を用いた生成物の検証テストを用意する

### 3.5 テンプレートの内部構造

検討事項:

- 対応先ごとにテンプレート全文を持つか
- 共通本文から対応先固有形式へ変換するか
- 対応先固有の差分をどのように表現するか
- テンプレートスキーマをどのようにバージョン管理するか

推奨案:

- 共通テンプレートと対応先アダプターを分離する
- 対応先固有の内容が必要な箇所だけ上書き可能にする
- すべてのテンプレートにスキーマバージョンを持たせる

### 3.6 CLIおよび生成物の言語

検討事項:

- CLIの表示を日本語、英語、または多言語対応のどれにするか
- 生成するスキル、ルール、サブエージェントの本文を何語にするか
- プロジェクトごとに生成言語を選択できるようにするか

推奨案:

- MVPのCLI表示は日本語とする
- 公式テンプレートの本文は英語に統一する
- 多言語対応は後続リリースで検討する

## 4. P1: 各機能の実装前に決定する事項

### 4.1 再実行時の挙動

検討事項:

- 初回導入済みのプロジェクトで`harness init`を再実行できるか
- 前回の選択内容を復元するか
- 新しい資産の追加だけを許可するか
- 既存資産の更新や削除を扱うか

推奨案:

- 再実行を許可する
- 前回の選択内容を初期表示する
- MVPでは追加と検証だけを扱う
- 編集済みファイルの更新および不要ファイルの削除は行わない

### 4.2 導入状態を記録する設定ファイル

検討事項:

- `.harness.yaml`などの状態ファイルを作成するか
- アプリケーション、対応先、技術スタック、選択項目を記録するか
- 状態ファイルをGit管理するか
- Harness本体およびテンプレートのバージョンを記録するか

推奨案:

- リポジトリルートに`.harness.yaml`を作成する
- Git管理する
- アプリケーションごとの選択内容と生成履歴を記録する

### 4.3 生成物の識別とユーザー編集の検出

検討事項:

- Harnessが生成したファイルをどのように識別するか
- ユーザーによる編集をどのように検出するか
- ファイル内へ生成コメントを追加するか

推奨案:

- 状態ファイルへ生成先、テンプレートID、テンプレートバージョン、コンテンツハッシュを記録する
- ハッシュが変化したファイルをユーザー編集済みとして扱う
- ユーザー編集済みファイルを自動上書きしない

### 4.4 既存ファイルとの競合解決

検討事項:

- 競合時に上書きを許可するか
- 別名生成を許可するか
- 差分表示を提供するか
- 非対話実行時の競合をどう扱うか

推奨案:

- MVPでは上書きを提供しない
- 既存ファイルの維持、生成予定内容の表示、別名生成、導入取り消しを提供する

### 4.5 複数アプリケーションへの書き込み保証

検討事項:

- 複数アプリケーションへの書き込みを完全に一括処理するか
- 途中失敗時のロールバックをどう実装するか
- 一時ファイルやバックアップをどこへ作成するか

推奨案:

- すべての生成内容を一時領域で準備してから反映する
- 反映失敗時はHarnessが作成した変更をロールバックする

### 4.6 ルールの依存関係と競合

検討事項:

- `requires`、`recommends`、`conflicts_with`を定義するか
- 必須依存を自動選択するか
- 競合するルールの同時選択を禁止するか

推奨案:

- `requires`は追加前に確認する
- `recommends`はおすすめ表示だけに使用する
- `conflicts_with`は理由を表示して同時選択を禁止する
- 依存ルールをユーザー確認なしに追加しない

### 4.7 サブエージェントの権限モデル

検討事項:

- 共通の能力名をどの粒度で定義するか
- 対応先固有のツール権限へどう変換するか
- シェル実行、ファイル書き込み、外部通信をどの役割へ許可するか

推奨案:

- 役割ごとに最小権限を定義する
- ReviewerおよびArchitectは原則として読み取り専用とする
- TesterおよびDebuggerには限定されたテスト実行能力を与える
- 破壊的操作や外部送信をデフォルトで許可しない

### 4.8 サブエージェントのMVP収録範囲

検討事項:

- Reviewer、Tester、Architect、Debuggerの4種類で開始するか
- Security ReviewerおよびDocumenterもMVPへ含めるか

推奨案:

- MVPはReviewer、Tester、Architect、Debuggerの4種類に限定する

### 4.9 技術スタックのバージョン対応

検討事項:

- どのメジャーバージョンまでテンプレート品質を保証するか
- EOLバージョンを検出した場合に導入を許可するか
- メジャーバージョンごとにテンプレートを分けるか

推奨案:

- バージョンを検出してテンプレートへコンテキストとして渡す
- EOLバージョンは警告するが、導入自体は選択可能にする
- 大きな非互換がある場合だけメジャーバージョン別テンプレートを用意する

### 4.10 検出ロジックと確信度

検討事項:

- 一つのファイルだけでスタックを確定するか
- `confirmed`、`likely`などの確信度を設けるか
- 親子ディレクトリにある重複候補をどう統合するか
- アプリケーション、サービス、ライブラリをどう分類するか

推奨案:

- 複数シグナルを用いて判定する
- `confirmed`、`likely`、`manual`、`conflicting`の状態を持つ
- 判定根拠をユーザーへ表示する

### 4.11 モノレポ内の共通設定

検討事項:

- リポジトリルートの共通ルールを許可するか
- 親から子への継承や上書きをどう扱うか
- 複数アプリケーションへ選択内容をコピーする機能を設けるか

推奨案:

- MVPでは暗黙の継承を提供しない
- 必要であれば明示的な選択内容のコピーだけを提供する

### 4.12 対話実行と非対話実行

検討事項:

- MVPでCI向けの非対話`init`を提供するか
- `--yes`、JSON出力、設定ファイル入力を提供するか
- `validate`の終了コードをどう定義するか

推奨案:

- MVPの`init`は対話実行を中心とする
- `validate`は非対話で実行可能にする
- 完全な非対話導入は後続リリースで追加する

## 5. P2: MVP期間中に決定する事項

### 5.1 プライバシーとテレメトリー

検討事項:

- 利用状況やエラー情報を収集するか
- 収集する場合のオプトイン、匿名化、保存期間
- 解析対象から除外する機密ファイル

推奨案:

- MVPではテレメトリーを収集しない
- プロジェクト情報を外部送信しない
- `.env`や資格情報ファイルを読み取らない
- ソースコード本文ではなく、既知の構成ファイルを中心に解析する

### 5.2 公式テンプレートの品質基準

検討事項:

- テンプレートのレビュー手順
- 公式ドキュメントとの整合性確認
- ライセンスおよび出典の記録方法
- 重複、危険なコマンド、古いAPIを検出する方法

推奨案:

- 各テンプレートに適用条件、対応バージョン、出典、ライセンスを記録する
- 対応先ごとのスナップショットテストと構文検証を必須にする
- フレームワーク公式規約と矛盾しないことをレビュー項目に含める

### 5.3 エラー表示とログ

検討事項:

- 通常表示と詳細ログをどのように分けるか
- エラーに対象ファイル、原因、修正方法をどこまで含めるか
- デバッグログへ機密情報が混入しないようにする方法

推奨案:

- 通常表示はユーザーが次に取るべき操作を中心にする
- 詳細ログは明示オプションで有効にする
- ファイル内容や環境変数を無条件にログ出力しない

### 5.4 性能上限

検討事項:

- 許容する解析時間
- 探索するディレクトリ階層とファイル数の上限
- 大規模モノレポでの除外ルール

推奨案:

- 既知のビルド成果物と依存ディレクトリを探索対象から除外する
- ファイル全文を読む前にパスとマニフェストを優先する
- 性能目標は代表的なモノレポを用いた計測後に確定する

### 5.5 アクセシビリティとターミナル互換性

検討事項:

- 色を使用できない環境への対応
- キーボードのみで全操作を完了できるか
- 非TTY環境での表示

推奨案:

- 色だけで状態を区別しない
- `NO_COLOR`相当の設定を尊重する
- すべての操作をキーボードで完了可能にする

## 6. 要件確定後に作成する詳細仕様

残課題の決定後、実装着手前に次の資料を作成する。

- CLI画面遷移図
- コマンドおよび終了コード仕様
- 公式テンプレート一覧
- テンプレートメタデータスキーマ
- 技術スタック検出ルール一覧
- 対応先アダプター仕様
- ファイル競合およびロールバック仕様
- 受け入れテストケース一覧
